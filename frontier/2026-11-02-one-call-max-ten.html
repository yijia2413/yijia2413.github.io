至多调用一次模型，工具检索在 AppWorld 上的限制

一项任务要用六个 API，检索只找到五个，召回率可以不错，任务却仍可能做不完。一篇工具检索预印本在 AppWorld 的 345 条多工具任务上发现：取前 16 个结果时，未在该测试池上训练、每条查询至多调用一次模型的方案，主表中找齐整套 API 的最高比例是 9.6%。附录消融达到 11.9%，因此 10% 不能视为这类结构的能力上限。

1前 16 个结果里，整套 API 很少齐全

工具目录放不进每次提示时，检索器先决定 Agent 看见哪些工具。一条请求要几个工具，缺一个，那一步就做不成。评测常用召回：所需工具里找回了多少。这篇用完整性：整套所需工具是否都在截断的前 k 个里。

依据论文摘要、第 5.1 节和表 2（HTML）。AppWorld 官方测试 345 条，每条所需 API 至少 2 个、中位 6 个，k = 16。论文摘要将未在该测试池训练、每条查询至多一次模型调用的方案概括为完整性不超过 10%；主表与附录消融需要分开看。主表七个代表臂里最高 0.096（依赖图 Graph-of-Skills，按表 4 的 312 条不完整反推，完整 33/345）。附录表 A1 有一个消融：只保留确定性边、建图也不调模型的 GoS，完整性 0.119。论文写它和 0.096 相近，配对区间含 0，未进主表。0.096 是主表最大值，不是结构族被测出的上限。BM25、MCP-Zero 是 0。分解加一次调用是 0.035。简化 HYSET 也是 0，但在测试池训练查询上训过，不进「未训」。训过的 COLT 是 0.328（113/345），层级导航 AnyTool 是 0.301（104/345），后者中位 31 次调用、约五分钟，不进「至多一次调用」。

MCP-Bench 103 条任务、257 个工具：同一截断下 COLT 完整性 0.583，AnyTool 0.398，未训一次调用那一组最高到分解的 0.359。和 AppWorld 这一截不要并进同一个范围。

2单工具任务会影响合计分数

为什么后面用 AppWorld 这种每条都要几个工具的池，而不是看 ToolRet 合计。

3六种结构、两套池

AppWorld：官方测试 345 条（test-normal 129、test-challenge 216），In-N-Out 池 456 个 API。所需集合是查询会调用的 API，加上能产出其参数的生产者。六个 supervisor API 始终交给 Agent，评分前从排名和所需集合里拿掉。剩下每条 2 到 12 个 API，中位 6。258 条是单链，87 条是多连通块。没有单 API、也没有全独立 API 的测试条。

MCP-Bench：28 个服务器、257 个工具、103 条任务。所需集合从任务详述和依赖分析里点名的工具来，限制在该任务的服务器上。一条只靠转述、没点名，剔除。六条单服务器任务只点一个工具，另外 97 条要几个。论文写这些是生成器计划里的参考集，不是唯一金标。

六个结构各选代表。能固定的共享件固定：稠密、分解、先服务器后工具、图这几臂用 bge-base-en-v1.5；所有模型步骤用 DeepSeek-V3.2、温度 0。COLT 和简化 HYSET 按作者协议在测试池的训练查询上训；其余按设计不训。

分解把 AppWorld 召回@16 从 bge 的 .190 抬到 .417，完整性只从 .020 到 .035。缺一个，整套仍不算完整。

主表中超过 10% 的 COLT 与 AnyTool，成本来源不同。COLT 查询时不再调模型，要同一工具池上的标注请求：AppWorld 90 条训练、57 条开发选检查点；MCP-Bench 按服务器数分层五折，每折 75 条。AnyTool 不用训练，AppWorld 中位 31 次调用、99,739 token、307 秒；MCP-Bench 中位 38 次、90,479 token、311 秒。分解和 MCP-Zero 一次调用，AppWorld 完整性不超过 .035。

失败也不一样。COLT 缺的 API 里 58%（404/698）排在 17 到 50，主要是截断深度。AnyTool 241 条不完整里，162 条主因是已经找到请求点名的 API，没把产出其输入的前置 API 收齐；538 个缺的 API 里 317 个是这一类。扁平、图、简化 HYSET 多半连目标 API 都没排进前 16。

4完整性对不对得上任务

本节讨论完整性这个指标，在官方 Agent 上值不值得看。数字来自论文第 5.5 节（HTML）。

官方 AppWorld 简化 ReAct 代码 Agent，提示和 DeepSeek-V3.2 配置（温度 0，最多 50 步），从两个官方测试切片里随机抽 60 条（normal 20、challenge 40）。两种暴露：金标所需 API（A），COLT 前 16（C）。只有暴露的 API 加 supervisor 能被文档化和调用，其它调用走 AppWorld 自己的错误。

A 成功 46/60，C 成功 23/60。只在 A 成功 25 条，只在 C 成功 2 条。精确 McNemar p = 5.6×10⁻⁶。论文写差几乎全来自不完整检索。完整和不完整是观察分组，完整任务可能更容易；限制写在图注和段末。

COLT 前 16 完整的 21 条：C 全成功，A 成功 20。不完整的 39 条：C 成功 2，A 成功 26。C 中位步数 32，A 是 19；碰到未暴露 API 错误 30 次对 8 次；提示 token 约 15.1 百万对 7.4 百万。完整和不完整的比较是观察性的。同一批不完整任务上金标暴露过了三分之二，论文把缺口从「任务更难」里拆开一截。

5工具检索需要检查整套完整性

多工具任务需要单独报告“整套所需工具是否找齐”。召回率、命中率或 nDCG 都有用，但不能替代这个问题。AppWorld 的 345 个任务中，分解检索可以把召回率提高到 .417，完整性却仍只有 .035。

采用相似度 top-k 检索时，还应区分：请求需要一个还是多个工具，k 取多少，遗漏的是目标 API 还是提供输入的前置 API，以及是否有同一工具池的标注请求可训练集合级检索。

我的判断是，目录大到无法在每次提示中完整提供时，需要同时衡量完整性和成本。一次分解可以提高召回，仍可能遗漏必需工具；有标注请求时可以比较集合级训练，没有标注、又能接受几分钟延迟时，可以比较层级导航。论文里后者在 AppWorld 上中位需要 31 次调用。两套工具目录其实都能放进所用模型的上下文：AppWorld 为 64,874 token，MCP-Bench 为 59,278 token，按 DeepSeek-V3.2 分词。完整提供的代价会在执行阶段反复出现，不能只比较一次检索的成本。

10-19 写过可见工具列表也是输入。10-29 写过第一次请求里工具定义占字符 63.2% 至 77.4%。那两篇动的是已经放进提示的工具清单。这篇动的是清单由检索截出来之后，整套还齐不齐。

6这篇没测到的

  • 主表的 9.6% 对应 AppWorld、345 条、k = 16、未在测试池上训练、每条查询至多一次模型调用。摘要概括为不超过 10%；主表最高为 0.096（33/345），附录消融达到 0.119，不能把 10% 当成结构上限。附录表 A1 确定性 GoS 消融是 0.119，论文写与 0.096 相近、区间含 0，未进主表。GoS 主臂建图时调过模型，查询时 0 次，仍进这一截。COLT 0.328 和 AnyTool 0.301 要标注或几十次调用，与主要比较的条件不同。MCP-Bench 上分解 0.359、COLT 0.583，不要和这一截并进同一个范围。
  • 这些比较使用的是 base 尺寸编码器，不能视为结构族的能力上限。第 7 节写稠密、分解、先服务器后工具、图这几臂用 bge-base 和 e5-base。更大的通用和工具专用编码器在 ToolRet 上更高，换编码器是后续工作。
  • 所有模型步骤都是 DeepSeek-V3.2。层级导航相对 COLT 的位置绑在导航模型上。论文转引 GatewayBench：GPT-5.4 换成 GPT-5.1，层级网关任务成功平均掉 37.6 个点，扁平网关掉 11.9。37.6 和 11.9 是别人的基准，不和 9.6 比。
  • 下游 21/21 对 2/39 是 60 条抽样、一个 Agent、COLT 的前 16。完整任务可能更容易。金标暴露在同一 39 条不完整上成功 26 条。没有对其它检索臂做同样的下游检查。金标暴露最多给 12 个 API，COLT 前 16 给 16 个，菜单大小不同。这一条是我的看法，论文没把它列为局限。
  • MCP-Bench 的所需集合是参考集。来自生成器计划，不是唯一金标。六条单工具任务留在 103 里。
  • HYSET 是简化臂，且训过。没有执行奖励，最大集合放到 13 和 20。AppWorld 完整性 0 不代表完整 HYSET，也不进「未训」。
  • 分解是通用重实现。没有已训练分解方法的公开代码。AnyTool 只跑搜索阶段，下游求解和自反思没跑。AnyTool 345 个池里 258 个不足 16 个 API，完整性@16 和固定长度列表不好直接比。
  • MCP-Zero 的 0 是改造后的数。服务器文本是占位句，调用从逐步请求改成单次，嵌入换成 bge。不代表「先服务器后工具」这类结构。
