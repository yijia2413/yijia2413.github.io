ScienceBoard 上，查过状态的误报 5.4%，生成脚本 21.7%

核验计算机任务是否完成，检查实际状态比只看一张截图更可靠。VeriCUA 先了解机器上下文，再选择界面或代码检查。在 ScienceBoard 的 169 个案例上，它的假阳性率为 5.4%；同样使用 gemini-3-flash-preview 的一次性生成脚本方案为 21.7%，单次视觉语言模型评审为 24.8%。弃权按失败计算。

1实际状态检查减少误报

计算机使用 Agent 跑完一条，常见核验是：把截图或轨迹交给视觉语言模型打一次分，或者按任务生成一段检查脚本对着机器跑一次。两条路都只看见当时给到的观察，或脚本猜到的状态位置。编辑没保存、操作失败没有提示、Agent 自己报完成，都可能被写成成功。

依据论文表 1 和附录 B.4。ScienceBoard 在线、169 例、官方评测器做金标、执行 Agent 和核验器都跑 gemini-3-flash-preview：VeriCUA 假阳性率 5.4%，自动生成核验器 21.7%，单次视觉语言模型评审 24.8%。成功是正类。弃权记成失败，不记成成功，所以弃权不加假阳性、会压召回。ScienceBoard 中，生成检查与目标科学软件不匹配的问题最明显；5.4 大约是生成脚本的四分之一。AndroidWorld 116 例是 7.7 对 16.9；OSWorld 361 例是 13.9 对 25.9。三列不要并进同一个范围。

附录 D.1 给了一条 AndroidWorld。指令要恰好一段新视频。媒体库读到开局之后多了三行，目录里三份文件，间隔一分钟。四次核验里三次判失败，一次弃权。Agent 报完成。单次评审和生成脚本都判成功。

2三个在线环境

在线核验发生在回合结束之后，对着还在的机器状态。AndroidWorld 跑模拟器，OSWorld 跑虚拟机，ScienceBoard 跑科学桌面。每条由该基准自己的脚手架执行。金标是各基准官方评测器。OSWorld 执行成功率 44.3%，ScienceBoard 23.7%。AndroidWorld 116 例写的是 M3A Agents，表 B.1 没有给执行成功率。

对照三条。视觉语言模型评审：一次调用，看给到的观察，出裁决或分数。自动生成核验器：每个任务生成一段评测脚本，对机器跑一次，二元裁决。VeriCUA：先看应用上下文，写出任务量表，再对还没落实的条目选界面检查或代码检查，按证据规则汇总。后两条只在在线设置里比；离线设置另有 CUAJudge 和 OS-Themis，与主要比较的条件不同。

主表 backbone 是 gemini-3-flash-preview。backbone 对照另跑 gemini-3.1-pro-preview，那一列不和 5.4 / 21.7 比。

3弃权不当成功

两条对照每条都给裁决。VeriCUA 在发现落不定任务、或者已经决定的几次核验互相打架时弃权。附录 B.4：弃权在一致率、精确率、召回、F1、假阳性率里都记成失败。已决定准确率另报。

ScienceBoard 已决定 70%，已决定准确率 91.6，总准确率 86.4。少掉的那截是弃权进了失败。假阳性率 5.4 不含把不确定写成成功。论文写这套口径偏向保守挑成功轨迹，用在数据筛选和奖励赋值。

第 5.3 节另写：三个在线环境里的虚假完成报告，AndroidWorld 用了一个子集，VeriCUA 拒掉约 80%。原文是 about 80%，没有条数分母，与主要比较的条件不同。差距在 ScienceBoard 最大：生成脚本很少拒掉错误的完成声明。

4只看屏幕，决定率 45%

附录表 C.1 是在线 AndroidWorld 的动作空间消融，对应正文图 3。只保留图形界面动作：决定率 45%，召回 57.6，准确率 77.0，假阳性 3/41，已决定准确率 87.9%。默认混合空间加上代码读状态：决定率 82%，召回 87.9，准确率 90.5，假阳性仍是 3/41，已决定准确率 95.1%。

论文写配对分析里，代码通道多出来的每条正确决定，都有文件或应用存储读取撑着。界面观察落不定的条目，存下来的状态能定。假阳性条数没有跟着涨。

离线核验是辅线。记录轨迹上 VeriCUA 仍高于对照，OSReward-Hard 284 条人工标签：准确率 70.4，对 OS-Themis 65.7、CUAJudge 63.4、TRM 57.4。WebArena 715 条里，记录解决不了任务时走初始判断回退，原文写发生在 23% 的轨迹。那一列没有机器可探，不能用来解释在线环境的 5.4% 假阳性率。

5核验要读取哪些实际状态

给计算机或浏览器 Agent 增加完成核验时，需要说清核验器能读到什么：一张截图、生成脚本所需的上下文，还是操作结束后的文件、数据库和设置。ScienceBoard 的 169 个案例中，先了解上下文再探索状态的假阳性率为 5.4%，一次生成脚本为 21.7%。

选择完成核验方法时，需要明确三点：评审能否读取操作结束后的持久状态，生成检查脚本前能否了解应用上下文，以及证据不足时能否弃权。仅写“增加完成评审”或“生成 checker”，还不足以定义核验行为。

我的判断是，不能直接把 Agent 自报完成或单次截图评审的成功，作为训练和奖励的正例。界面显示完成而存储中没有对应记录，是附录 D.1 视频所展示的失败类型。支付、邮件和配置修改等任务，可以据此考虑增加操作结束后的持久状态检查；论文没有验证这些具体部署建议。

10-14 写过复现成功撑不起联合验收。10-28 写过第一阶段通过率高于整条终检。10-31 写过未核计划终局 0.94、整条可执行 0.47。那三篇动的是测试池、阶段、工具前缀。这篇动的是完成声明有没有对着机器状态查过。

6这篇没测到的

  • 5.4 / 21.7 的比较来自 ScienceBoard 在线、169 例、flash backbone、弃权记失败。AndroidWorld 7.7 / 16.9，OSWorld 13.9 / 25.9，不要和 5.4 / 21.7 并进同一个范围。表 1 假阳性率没有整数分母。表 C.1 的 3/41 仅对应 AndroidWorld 的动作消融。
  • 虚假完成「约 80%」没有条数。第 5.3 节写 about 80%，AndroidWorld 用子集，图 5b。不和 5.4 比大小。
  • 生成脚本在 OSWorld、ScienceBoard 上召回更高。总准确率和假阳性率是另一列。挑成功轨迹和追全成功，口径不同。
  • 代价按数量级写。附录 E：一次核验对每条轨迹发出数十次工具调用和模型调用，比单次评审高一个数量级。表 C.9：在线第一套 VeriCUA 39.2K token、97 秒，生成脚本 16.2K、60 秒。离线 OSReward 上 VeriCUA 345K–378K，三个单次评审合计 33K–35K。论文写更适合筛选和奖励赋值，不适合交互使用。
  • 金标也会错。附录 C.6：814 条记录轨迹里，已决定的 VeriCUA 和金标打架 81 条；换一家模型的盲审支持 VeriCUA 51 条、反对 20、不确定 10，不确定留在分母，51/81 ≈ 63%。在线 OSWorld：VeriCUA 的 28 次假阳性里，约 18 次是官方评测器把失败标错。这两项是对金标差异的补充分析。
  • 只读。论文写 VeriCUA 从不写入被核验的环境。不能回放到不能插桩的机器上。随机核验要把多次抽样的离散写在每次比较旁边。
