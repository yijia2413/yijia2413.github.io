第一次过测之后，成功跑里中位还剩 35% 到 60% 的步

编码 Agent 第一次写出能过官方测试的补丁，往往还不会停。一篇预印本在 OpenHands 上对每一步的仓库补丁做离线评测：核心设置里，最终提交仍过测的那些跑，第一次过测之后的步占整条轨迹的中位比例，Qwen3-Coder 是 35% 和 37%，Laguna-XS.2 是 60% 和 54%。过测之后的步大半在跑测试、写检查、翻仓库。Agent 当时看不见这些官方测试。稿件推断：线上不能照抄「第一次过测就交」。

1过测和停下差多少步

Termination Lag: Coding Agents Solve Early but Stop Late 盯的是仓库级修 bug：给一条 issue 和一份仓库，Agent 查文件、改代码、跑命令，最后交补丁。SWE-bench 只看最终补丁过不过任务测试。原文设想的例子：两个 Agent 都在第 10 步写出同一份正确补丁，一个立刻交，一个再跑 40 步复测、看调用方、看 diff，分数一样。

作者把轨迹拆成两段。第一次过官方测试的步记为 F，Agent 自己停下的步记为 S。终止滞后 TL = S − F。归一化滞后 NTL = (S − F) / S，分母是该条轨迹的总步数。表 1 的 TTFCP、S、TL、NTL 都是成功跑上各自取的中位数：最终提交仍过测的那些轨迹。中位数不可相加，NTL 中位数也不能用表里的 TL 中位去除以 S 中位反推。Qwen Verified 一列是 30、48、16、35%，48 − 30 = 18，不是 16；16 / 48 约 33%，不是 35%。

2怎么量第一次过测

主框架是 OpenHands，五个模型都跑过。Qwen3-Coder-30B-A3B 和 Laguna-XS.2 走 vLLM，步数预算分别是 100 和 250，上下文窗口 131K 和 256K。Haiku 5.5 和 GPT-6 Luna 走 Anthropic / OpenAI 接口，预算 100 步。Seed-OSS-36B 另跑 SWE-bench Pro，预算 150 步。每条任务跑一次。Qwen 和 Laguna 的预算、窗口都不同，S 的上限也不同；图 2 把两者并排，只展示各自的 NTL，不比较模型优劣。

每一步——模型推理、选动作、工具执行——作者在 Agent 等下一轮模型回复时，用日志代理把当前仓库相对任务基线提交的 diff 存下来，补丁用临时 Git index 构造，不改 Agent 的工作仓库。评测在隔离容器里走官方手续，相同补丁只评一次。Agent 收不到这次评测的任何反馈。官方测试对它是隐藏的，它只能靠自己跑的检查来判断能不能停。

S 取 Agent 自己停下的那一步。碰到步数或上下文上限的成功跑，每个设置里有 1% 到 4%，按最后一步计。步数近似计算开销，原文没有把滞后换成 token 账单。

4过测之后在干什么

成功跑上，作者按记录下来的工具和参数，把第一次过测之后的每一步分成五类。核验：跑仓库已有测试、另写测试、构建。探索：看文件、搜仓库、用 Git 看改动。再改源码：继续改实现。收尾：删临时文件、交最终回复。其余记成推理或其他。

核验在每个评过的设置里都是最大一类，占终止滞后步的 48% 到 63%。探索另占 15% 到 29%。Qwen、Laguna、GPT-6 Luna 再改源码只占 2% 到 6%；Seed-OSS 在 Pro 上是 19%。这些百分比的分母是第一次过测之后的步，不是整条轨迹。原文未说明是把所有成功跑的步合并后算占比，还是逐条占比再取中位。

补丁本身的结局换了分母：到达过正确补丁的轨迹里，61% 到 96% 一直保持到结束。后来改坏又修好的，六个设置是 3% 到 31%；原文点名的三格是 Laguna Verified 11%、Multilingual 31%、Seed-OSS Pro 17%。后来改坏并且最终没交过的，六个设置里是 1% 到 8%。对这 1% 到 8%，停在第一次过测会保住官方过测；原文没有另报「若当时停下，总过测率会高多少」。

5你的运行位

看最终过测率，看不出第一次过测之后还跑了多久。自己的日志如果逐步留了仓库 diff，可以事后用同一套隐藏测试回放，画出 F 和 S。这是诊断，不是线上停止器：论文的 F 用了 Agent 当时拿不到的官方测试。

过测之后的步大半在核验和翻仓库。稿件推断：运行位上如果只按「再改一次源码才算还在干活」来估成本，会把核验步漏掉。表 1 里从第一次过测到停下，模型输入上下文还相对涨了 28% 到 78%。

1% 到 8% 的到达过正确补丁的轨迹，后来改坏并交了错误补丁。稿件推断：继续跑有时会把已经过测的东西改掉。论文没给出一个只用 Agent 自己证据的停止规则，也没测「核验多少步才够」。

和已有几篇相邻：失败预测里，题目难度对照比仿 Fail-Fast 的轨迹预测高；终局成功，整条轨迹仍可能有一步执行不了；过期测试命令让 Sonnet 多调用约两次工具。这里多出来的是：最终过测的那些跑，中位仍有三分之一到一半以上的步发生在第一次过测之后。

6这篇没测到的

三个基准、五个模型、两套框架，每条任务一次。作者写可能搬不到别的设置。步数类别靠工具和参数的规则，不是人工标注。Seed-OSS 在 Pro 上过测任务少，表 2、表 3 那一列样本小。SWE-bench Pro 的任务总数原文这一节没写。NTL 以最终过测为条件：Multilingual 上 Qwen 只有 22.3% 的任务进入统计。原文没报各格成功跑的条数，也没报 Haiku、Luna 的成功率和成功跑条数，附录中位数样本量不详。

神谕停在第一次过测，保住的是原来就过测的任务，没有声称能抬高总过测率。Agent 运行时看不见官方测试，核验步不一定多余。闭源模型只跑了 Verified；换框架只测了 Qwen3-Coder 加 mini-SWE-agent。

写作时没有复跑作者的容器，数字从 HTML 全文抄。
