SWE-bench Verified 上，过测补丁多出来的 61% 是测试

一篇预印本把 GitHub Copilot CLI 上 18 个模型、7,660 条已经过测的轨迹拆成块。「多出来的编辑」是未打分的测试文件改动，加上任务测试口径下不需要的块；测试改动没测过必要性。SWE-bench Verified 上中位模型改的行是开发者补丁的 2.33 倍。按块计，多出来的里测试文件 61%、文档 13%、代码 21%。DeepSWE 上同一口径代码 58%、测试 26%。代码块必要性均值 0.887，开发者同一批实例 0.864，都是任务测试口径；这一口径下 18 家里 11 家比开发者少。加上行为探针后，12 家比开发者多、0 家少。任务测试下平均 11% 的代码块不需要；探针跑过的 3,559 个里 89% 会改行为，其中 35.5% 和开发者补丁一致。

1行数多，不等于调试残留

预印本 How Much Do Coding Agents Over-Edit, and Why?（Goel、Steenhoek、Hu，Microsoft，2026-11-25）看的是已经过测的仓库级补丁。本篇只论一件事：SWE-bench Verified 上按块计，多出来的主体是测试文件。后面几节是这 61% 里剩下那 21% 代码块是什么、从哪来、事后能不能剪，不另立一个判断。作者写：补丁更大，常被读成改多了。行数说不出多出来的块要不要、是什么、从哪一步写进去。

方法叫 Delta Residue Attribution（DRA）。回放轨迹，把最终补丁切成可单独撤回的块（同一文件里相邻改动，中间最多隔一行未改行就合并；新建或删除的文件算一块），每块追到最后写过其中一行的那一步。撤回这一块，再跑任务测试：测试挂了算需要，仍过算不需要。SWE-bench 用 FAIL_TO_PASS 和 PASS_TO_PASS；DeepSWE 用任务自带测试。只分析已过测补丁。测试文件改动在 SWE-bench 评分里会被重置，作者单独记成未打分，和不需要的块合称「多出来的编辑」。主指标是代码块里需要的比例，写作 NP_code。

语料：GitHub Copilot CLI，18 个模型。SWE-bench Verified 500 道 Python 题，过测率 64.0% 到 89.4%；DeepSWE 113 道长程题（Go、TypeScript、Python、Rust、JavaScript）。主结果 6,728 条 SWE-bench Verified 补丁（30,265 块；482 个不同实例，114 个 18 家都有）和 932 条 DeepSWE 补丁（26,209 块）。开发者基线：SWE-bench Verified 470 个实例、1,317 个代码块；DeepSWE 103 道有开发者补丁且过测的题（4 份开发者补丁不过测，丢掉）。SWE-bench Verified 轨迹回放与提交补丁完全一致的占 96.7%。

按行数，SWE-bench Verified 上中位模型改的行是开发者补丁的 2.33 倍（模型间 0.94–5.10）。只看非测试文件，中位比值 1.09（0.79–2.03）。只看代码块，比值 0.86，按题中位 1.00。按必要性，任务测试口径下 Agent 代码块均值 0.887，同一批实例上开发者 0.864。开发者补丁在任务测试下也有 33% 的代码块（434 / 1,317）被标成不需要；行为探针加强后，开发者只剩 3% 不需要，Agent 均值从 0.887 到 0.925。作者把不需要份额写成对真实多余的上界，比较时两边用同一套测试。

2多出来的是什么

SWE-bench Verified 上，按块计的多出来的编辑：测试文件 61%、代码 21%、文档 13%、注释或格式 5%。测试改动一律记入、没测过必要性；代码块只有被任务测试判成不需要的才记入。原文写评审可能欢迎其中不少测试。81.5% 的 Agent 补丁改了测试文件。DeepSWE 反过来：题是功能实现，每条补丁大约多六倍块；代码占多出来的 58%，测试 26%，文档 12%。行口径是另一个数：SWE-bench Verified 上 60% 的 Agent 改动行在测试文件里。

SWE-bench Verified 上 3,987 个不需要的代码块里，行为探针跑了 3,559 个：89%（3,151 / 3,559，95% Wilson 区间 [87, 90]）撤回后行为会变。原文表 7 把这 3,151 个拆开：1,263 个（35.5%）开发者补丁的行为和完整 Agent 补丁一致，探针口径下算需要；1,586 个（44.6%）和拿掉这块一致；133 个（3.7%）混合；169 个（4.7%）两者都不像；408 个（11.5%）探针上看不出差别。同一套探针下，开发者不需要的代码块 363 / 432（84%，[80, 87]）也会改行为。

作者在 271 道过有效性检查的 SWE-bench Verified 题上，用 mutmut 往打过补丁的代码里注入 1,962 个小人工缺陷。Agent 新加的测试杀掉 68.1%；同一批被改过的测试文件里原有回归测试 45.6%；任务测试 77.1%。Agent 测试对需要的代码里的缺陷杀掉 73.2%，对不需要的代码里 31.2%。任务测试漏掉的缺陷里，22.7%（102 个，占全部缺陷 5.2%）被 Agent 新加或加强的测试抓住。附录 D.2：5,439 条改了测试且有步骤来源的补丁里，52.0% 把全部留下的测试写在最后一次需要的代码改动之后；8.7% 看到测试先红后绿。

3不需要的代码从哪一步来

如果残留主要来自调试，它会在探索、复现、打探步骤写进去，后来没被撤回。调试角色在正文里是这三步，不含修订。块归到最后写过其中一行的那一步：先在调试步写、后在修复步改的，算修复。全体残留块里，调试步骤占比 0.257；4,898 个调试步骤残留块里 4,676 个是测试文件，Agent 在修之前当回归测试写的。代码残留里，只有 154 / 3,987（55 条补丁）来自调试步骤，代码调试份额 0.039。把修订也算进调试，代码调试份额升到 0.148，仍低于注册时的杀掉线 0.15。草稿脚本和调试打印几乎进不了过测补丁。

修复步骤写下 83% 的不需要代码，修订步骤 11%。修订时写下的代码不需要的比例，只比第一次修复略高（0.29 对 0.25）。DeepSWE 上，有精确来源的块里，代码调试份额 0.037；修复步骤贡献 72% 的不需要代码，修订 22%，不需要率 0.24 和 0.27。

步骤角色先走两条规则，其余由 GPT-6.1 Sol 看议题、压缩历史、动作和叙述来标。主评审和第二评审 Opus 5.5、探针评审 GPT-6 Astra 都在被评估的 18 家里。第二评审在 10,000 个随机抽样步骤上，细角色一致 84.4%，调试对非调试 89.1%（κ=0.55）。没有人工抽查。最常见分歧是第二评审把「复现」标成「修复」（786 步）。主评审多标复现、少标修复，这个偏差会抬高调试份额；代码调试份额低，没有被这个偏差撑起来。

4过测率带不走必要性

SWE-bench Verified 上 18 个模型，过测率与 NP_code 的 Spearman 相关 −0.10（原始 p=0.69；按每个模型的实例自助，95% 区间 [−0.28, +0.05]）。过测率几乎一样时：Sonnet 5 80.6%、NP_code 0.922；Gemini 3.7 Flash 81.4%、0.789。后者每个任务留下的不需要代码块大约是前者的 3.6 倍（1.23 对 0.34）。

相对开发者，任务测试口径：11 家显著更少不需要代码（GPT-6 Astra 只是边缘，区间下界 0.002）；4 家看不出差别（Kimi K3、Claude Haiku 4.5、GPT-6 Sol、GPT-6.1 Sol），看不出差别不等于等价；3 家显著更多：Gemini 3.8 / 3.7 / 3.6 Flash。NP_code 分别是 0.765 [0.735, 0.793]、0.789 [0.759, 0.820]、0.791 [0.760, 0.820]，对开发者的差是 −0.095 [−0.129, −0.064]、−0.074 [−0.107, −0.042]、−0.076 [−0.111, −0.041]。加上行为探针后，12 家比开发者多、0 家少；差值从 +2.3 个百分点翻成 −4.5。

DeepSWE 上 Agent 均值 0.797，103 份开发者补丁 0.785；两家显著低于开发者，没有一家显著高于。过测率与 NP_code 负相关：Spearman −0.59（p=0.01，n=17，每家至少 10 道已评分题）；按题调整后 −0.52（p=0.03）。两套基准上模型名次中等相关（+0.59）。Gemini 3.7 和 3.8 Flash 两边都低。

作者主文用任务测试口径，并写明开发者基线。附录里配对了别的 harness 的最终补丁：Claude Code 三家在 SWE-bench Verified 上 0.926（同一批题 Copilot CLI 0.923）；DeepSWE 上 Codex CLI 六家 GPT 0.787（CLI 0.794）。这是最终补丁，没有把角色推广到 Copilot CLI 以外。

6,728 条里 4,860 条在第一次改源码之后，对自己的测试跑到过全绿；其中 3,035 条（62%）之后还继续改。停在第一次全绿只覆盖全绿之后还继续改的补丁，所以这一列基线 NP_code 是 0.700，另外三列是 0.924–0.936。3,031 条打过分的补丁里 2,948 条（97.3%）任务测试仍过，代码块从 7,419 落到 7,269，NP_code 只从 0.700 到 0.710。仍过测且内容有变的 2,939 条里，事后改动碰到源码块的 208 条，只碰测试、文档或配置 1,472 条，cancel out 1,259 条（原文没写这 1,259 条里有没有源码改动）。不需要的代码多半在自己的测试第一次全绿时已经在补丁里。

自己审：17 / 18 家（没有 Kimi K3 的 Copilot CLI 审稿模型；Opus 5 由 Claude Opus 5.5 审，Opus 4.8 由 Claude Opus 4.6，GPT-5.6 Terra 由 GPT-6.1 Terra；跳过 4 个超长补丁），6,345 条补丁、13,729 个代码块；1,540 条至少丢掉一块。丢掉的代码块里 813 / 1,238 与探针口径下的不需要对齐，精确率 65.7%、召回 35.5%；任务测试口径下是 78.5% / 28.8%。丢掉会弄坏 1.8% 已过测补丁（探针口径下仍过 98.2%）。在探针口径的不需要块里，开发者补丁的行为像拿掉这块的，丢掉 40.5%；行为像完整补丁的，丢掉 14.7%；需要的块丢掉 2.6%。

DRA 剪枝只覆盖 2,495 / 6,724：3,777 条轨迹里抽不出独立测试选择器，450 条基线重复跑不过。2,495 条里 1,468 条只有一个代码块，清理从不撤最后一个代码块，所以这 1,468 条是空操作；可剪的是另外 1,027 条。精确率和召回对的是探针口径。用 Agent 自己的测试命令加上仓库已有 PASS_TO_PASS：召回 67.3%，精确率 46.3%，89.1% 仍过任务测试（分母含那 59% 不会被剪的补丁）。只用自己的测试：精确率 39.6%、召回 66.5%、86.6% 仍过。误删的多半是现有测试和 Agent 测试都没练到的行为。表 1 题注和附录表 21 把 DRA 列的「仍过」写成探针口径，5.5 节正文写成任务测试，原文自己不一致；这里跟 5.5 节正文。

6你的运行位

看行数会把测试文件算进「改多了」。SWE-bench Verified 上 60% 的 Agent 改动行在测试文件里；全块 NP 均值 0.472，模型间从 GPT-6.1 Sol 的 0.273 到 Sonnet 5.5 的 0.848，跟着写了多少测试走。评审欢迎测试的话，这一列不该和代码残留加在一起。

代码残留主要写在构造和修订修复的时候，调试步骤几乎带不走（Explore / Reproduce / Probe，最后一步归属）。循环里清打印、清草稿，对过测补丁里剩下的不需要代码用处不大；作者没测循环中清理。生成后再剪，精确率和召回是探针口径：自己审 65.7% / 35.5%；能抽出独立测试命令的 2,495 条里可剪的是 1,027 条，用自己的测试加仓库回归，召回 67.3%、精确率 46.3%，任务测试仍过 89.1%（分母含 1,468 条空操作）。

过测率高的模型，代码不一定更干净。SWE-bench Verified 上相关接近 0；DeepSWE 上过测更高的模型留下更多不需要代码。作者建议基准在过测率旁边报 NP_code，并带同一套测试打过的开发者基线。

和 11-13 第一次过测之后还剩步 管的是成功跑里中位还剩多少步；这篇管的是已经提交的补丁里，哪些代码块拿掉测试仍过。第一次全绿之后还继续改的那批里，碰到源码块的 208 条，只碰测试、文档或配置 1,472 条。和 11-13 是否同一条缝，是作者推断，计量单位不同。

7这篇没测到的

  • 必要性跟着测试走。DeepSWE 上开发者基线已经是 0.785，不需要份额是上界。行为探针由 GPT-6.1 Sol 写；第二评审 Opus 5.5 在 388 个两边都判的块上，改行为的比例 81% 对 89%。
  • 一次撤一块。成对才需要、一块里混了需要和不需要的行，会判错。
  • 只看过测轨迹。失败轨迹里的改多了没测。
  • 角色没有人工抽查。调试份额建立在 154 / 3,987 个代码残留块上。变异测试覆盖 271 题、1,962 个缺陷。
  • 回放：SWE-bench Verified 3.3% 对不上（228 次回放不一致、6 次自检失败、5 个二进制补丁）。DeepSWE 33.4% 的补丁（311 / 932）至少有一块没有来源（占块 14.9%，占代码块 12.7%）。
  • 主结果是 Copilot CLI。SWE-bench Verified 只有 Python，作者写可能被污染。人工是否同意「该删」只准备了协议，没有人标（附录 B.5）。
  • 注册假设用全体块的调试份额（0.257，落在杀掉线 0.15 和支持线 0.40 之间）。事后改成代码块份额 0.039，才低于杀掉线。循环中的撤回-拒绝和最小改动提示没跑，因为目标是调试步骤留下的代码。
