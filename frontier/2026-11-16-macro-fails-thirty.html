原生看对的判分，宏抽象后 31.0% 站不住

用模型给 Agent 轨迹打分时，线上往往先把工具合成宏、把一段交给子 Agent、或把早段历史压掉，再把剩下的给评审。一篇预印本把同一条冻住的轨迹做成原生、抽象、还原三套视图，任务、结局、金标、评审模型和评分标准都不变，只改评审看得见的证据。在原生视图上已经判对的那些条里，宏抽象后 31.0% 变成错判或没有可用结论，委派 30.9%，历史压缩 20.3%。分母是原生判对的条数，四个基准、七个骨干、四种协议按分子分母相加；同一宏抽象下，直接判 16.4%，再审一轮 49.3%，读者用的是其中一种协议。把对应出处还回去，这些失败里 85.5% 能回到正确结论；已经扛过抽象的条，还原后只有 5.2% 被改坏。原文没有按错判和没有结论拆开这 85.5%。

1同一条轨迹，换一层外壳

Do Verifier Judgments Survive Abstraction? Measuring Verification Transport for LLM Agent Evaluation 问的是：一条已经发生过的 Agent 轨迹，评审在完整记录上判对了，换成宏动作、委派边界或压缩历史之后，这个结论还在不在。作者把这件事叫 Verification Transport。失败有两种：给出了任务级结论但和金标不一致，或给不出可用结论。弃权算覆盖丢失，不算错判；两种分开报，加起来就是运输失败率 VTFR。

VTFR 只在原生视图已经判对的条上算。它不回答评审整体有多准，只回答：已经对的那些，换一层可见性之后还能否站住。原生准确率写成 C0 OBA，是操作平衡准确率；多阶段协议用最后一轮任务结论。池化率按各格分子分母相加，不把各格百分比再平均一遍。

四个基准都是已经发生过的轨迹，评测前做成匹配的原生 / 抽象 / 还原视图，不再跑 Agent、不再调工具。AgentProcessBench 250 条，对着轨迹里指定的那一条消息、用该步金标，不把整条轨迹的标签加总。ATBench 758 条工具使用轨迹。PlanRewardBench 441 对两两比较；两条候选都够格就一起抽象，否则只改够格的那一条，偏好标签和左右顺序不变。AgentDojo 754 条。这些计数是满足匹配构造资格的实例，温度 0，结构化输出再映射到各基准的标签空间。

七个评审骨干：Gemini-3.7-Flash、Gemini-2.5-Flash、GPT-OSS-120B、GPT-OSS-20B、Gemma-4-31B、Gemma-4-26B-A4B、Llama-4-Maverick。四种协议共用同一骨干、同一评分标准和同一轨迹表示，只改证据怎么用：V-LLM 一遍直接判；V-EVIDENCE 先写看得见的证据够不够再下结论，拿不到当前视图没有的出处；V-AGENTIC 证据不够可以要出处，出处仍来自同一条冻住的轨迹；V-DELIBERATIVE 把对应的冻住 V-EVIDENCE 结论当第一阶段 D1，再做一轮证据审计 D2，D2 看不到额外出处。D2 在原生视图上就会改结论，若干模型–基准格上原生成绩明显低于冻住的 D1。

2三种边界怎么造

宏抽象挑一段至少含两对完整「工具调用 → 工具结果」的连续块，对外只露出一个宏边界，内部操作和中间观察藏起来。委派把至少一对完整工具执行放到委派边界后面，评审看见委派和返回结果，看不见内部轨迹；没有真的起一个工人 Agent，任务也不重跑。历史压缩把更早的证据换成压缩边界标记，近段仍可见，并且保留最后一对工具调用和结果。还原把同一条原始轨迹里对应的事件原样塞回去，不重写、不补造。

附录 B.3 写了四条有效性：三套视图对着同一任务和同一条冻住的源执行；构造阶段不重跑任何 Agent、子 Agent、工具或环境；每个边界留着指向源事件的精确链接；变换确定、不看标签。差出来的判分，作者把它记在评审看得见的证据上，不记在执行本身变了。

331.0、30.9、20.3

四个基准、七个骨干、四种协议加在一起，原生已经判对的那些条里：宏抽象 VTFR 31.0%，委派 30.9%，压缩 20.3%。宏和委派的差在点估计里只有 0.1，区间见附录 F 图 6，正文没抄上下界。四个基准各自汇总也是宏和委派更高：宏 25.5%–32.2%，委派 26.1%–32.9%，压缩 16.2%–24.7%。骨干之间幅度差得大，方向一样。原文没有说明三种边界的原生判对集合是否相同，并排比较时分母可能不是同一批条。表 1、表 2 是点估计。

表 4 把失败拆成错判和没有结论，分母仍是原生判对的那些条。宏：错判 13.4%，没有结论 17.7%。委派：13.2% 和 17.7%。压缩：12.2% 和 8.0%，总数更低，错判占比相对更高。

消融只在 AgentProcessBench 和 ATBench 上，模型只有 Gemini-2.5-Flash 和 GPT-OSS-120B。A25 / A50 / A75 藏掉选定执行块里大约 25%、50%、75% 的够格语义证据原子，剩下的顺序和结构不动。四个模型–基准组合上，A75 的 VTFR 都高于 A25：AgentProcessBench 上 Gemini 24.3% → 31.4%，GPT-OSS 21.5% → 29.6%；ATBench 上 17.7% → 21.1% 和 16.9% → 22.9%。A50 不是每一格都单调。失败量随藏掉的证据变多而升高，不只是因为出现了一个边界标记。

4四种协议的两种掉法

四种协议的池化 VTFR 差一截。宏 / 委派 / 压缩：V-LLM 16.4%、17.3%、14.1%；V-AGENTIC 25.0%、23.6%、18.2%；V-EVIDENCE 34.5%、34.0%、18.7%；V-DELIBERATIVE 49.3%、50.2%、30.7%。附录 D 里 V-LLM 必须做强制二分类，不能弃权、不能要隐藏出处；V-EVIDENCE 和 V-DELIBERATIVE 可以弃权。失败形态跟着允许的输出走：直接判几乎总给出结论，错了也给；可以弃权的协议常常改成不给结论。V-AGENTIC 的提示也写了不要输出 ABSTAIN，宏抽象上仍有 7.5% 没有结论，原文没解释这一截怎么来的。

表 4 里 V-LLM 的没有结论三格都低于 1%。V-EVIDENCE 在宏和委派上没有结论是 24.0% 和 23.6%。V-DELIBERATIVE 到 39.9% 和 41.0%。V-AGENTIC 夹在中间。跨协议不能直接比谁更可靠：VTFR 的分母是该协议自己原生判对的子集，各协议对着的条并不相同。

表 5 的覆盖、假放行、假拒绝是三种抽象池化后的率。覆盖分母是该观察条件下全部四基准上的条。PRR 分母是抽象条件下的全部实例，不是原生判对的那些条。假放行 FCR 和假拒绝 FRR 只在 ATBench 和 AgentDojo 上算。FCR 的分母是金标为负且原生判负的条，FRR 的分母是金标为正且原生判正的条，两格不能直接比。V-LLM 抽象后覆盖 98.7%，FCR 41.3%，这一截最高。V-AGENTIC 的 FRR 13.1% 最高，要出处的比例合计 37.4%，宏 43.3%、委派 44.5%、压缩 24.3%。V-DELIBERATIVE 的第二阶段修回 8.7% 一开始就不对或不可用的条（BRR），同时把 28.5% 一开始就对的条改坏（HRR）。多想一轮没有新出处，会改掉已经站得住的结论。

骨干和协议是一起变的。V-LLM 池化 VTFR 从 Gemini-3.7-Flash 的 10.1% 到 Llama-4-Maverick 的 22.0%。V-DELIBERATIVE 在 GPT-OSS-120B 上 57.9%，Gemma-4-31B 55.2%，Gemini-3.7-Flash 49.7%，Llama-4-Maverick 46.4%；同一协议在 Gemma-4-26B-A4B 上只有 14.5%。没有结论占失败的份额，Gemini-3.7-Flash 配 V-DELIBERATIVE 是 91.4%，Gemma-4-31B 是 83.5%，GPT-OSS-120B 和 Gemini-2.5-Flash 都是 76.3%。

5把出处还回去

还原把该边界对应的原始事件还给评审。四个基准、七个骨干、四种协议加在一起，运输失败里 85.5% 回到正确结论；已经扛过抽象的条，还原后 5.2% 被改坏。宏：恢复 87.9%，劣化 5.3%。委派：86.9% 和 5.4%。压缩：恢复 79.8%，劣化 4.9%。压缩的还原条件写成把原始历史原样塞回去。摘要里 recovery is lower when provenance is lossy or unavailable 指的是 LossyR 消融，不是压缩这一格。原文没有按错判和没有结论拆开 85.5%。

出处保真消融仍是那两个模型、两个基准。失败之后三种补法：Requery 用同一份抽象证据再问一遍；LossyR 还原有序的动作和工具名，去掉参数、观察和文本；ExactR 还原该边界的完整冻住处。恢复率 Requery < LossyR < ExactR。AgentProcessBench：Gemini 22.5% → 42.8% → 80.0%，GPT-OSS 24.6% → 34.0% → 82.5%。ATBench：Gemini 33.1% → 53.9% → 81.9%，GPT-OSS 30.2% → 47.2% → 73.6%。再评一次不够，缺参数的出处也不够，完整出处才把大多数失败拉回来。

6你的运行位

自己的运行位如果先把工具收成宏、把一段交给子 Agent、或把早段历史压成摘要，再拿模型给这条轨迹打分、当奖励、当放行，这篇预印本测的就是评审看见的那一层。原生视图上的准确率不能带到抽象之后。31.0% 是四种协议混在一起的数；自己线上用的是其中一种。宏抽象下直接判 16.4%，再审一轮 49.3%。直接判的提示禁止弃权，失败形态是错判；可以弃权的协议失败形态常常是不给结论。选协议时看自己那一行，不要只看混合的 31.0%。

标题里的 31.0% 是宏抽象、四基准 × 七骨干 × 四协议、原生已经判对的那些条。委派 30.9%，压缩 20.3%。还原按原文能找回 85.5%。稿件推断：线上若拿不到精确出处，恢复率可能接近 LossyR 那一截，原文没有测压缩下的有损还原。

和已有几篇相邻：评审团更一致了，和人的一致没有跟着涨 讲的是改评分标准；同一批样本换一批，模型评审也会改判 讲的是同批评审互相带动；Hermes 压缩后规则还在，违规率仍高于完整历史 讲的是执行方自己还在违规。后两篇的具体数字以各篇原文为准，本轮没有重开。这里多出来的是：执行没变，评审看见的外壳变了，已经对的判分也会掉。

7这篇没测到的

三种边界是作者按冻住轨迹构造的，不是线上跑起来时自然长出来的宏、委派和压缩。还原假定原始出处还能塞回去。VTFR 以原生判对为条件，不刻画评审整体能力。四个基准、七个骨干、四种协议之外的领域和评审设计，原文标成可能不同。

稿件提醒，不是原文声明：表 1 里若干格的原生 C0 OBA 在 40%–50%，例如 AgentProcessBench 上 Gemini-2.5-Flash 43.0、GPT-OSS-120B 48.0、GPT-OSS-20B 50.7。这些格里「原生判对」会混进碰巧对的条。原文没有同视图重判或无信息边界标记这类零对照。消融里 A25 已有 17%–24% 的 VTFR，原文没有把这一截从抽象本身拆开。31.0% 里有多少来自碰巧判对，原文没分开。

严重度和保真消融只有 Gemini-2.5-Flash 与 GPT-OSS-120B，基准只有 AgentProcessBench 和 ATBench。FCR / FRR 只有 ATBench 和 AgentDojo。表 1、表 2 是点估计，区间在附录 F 的图里，正文没有逐格抄出上下界。原文没有按失败类型拆 85.5% 的恢复率。论文声明代码在 github.com/Disha1001/Verification-Transport，本轮打开该仓库返回 404，没有复核发布物。
